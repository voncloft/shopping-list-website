INSTALL
1. Keep a backup of your live database and the PHP file below.
2. Copy the supplied recipes/ingredients and recipes/steps files into the same
   folders in your site. These are plain HTML fragments in your existing format.
3. Run import_instant_pot_recipes.sql in your existing shopping_list database.
   Example: mysql -u YOUR_USER -p shopping_list < import_instant_pot_recipes.sql
   A normal SQL import in phpMyAdmin works too. Do not use --force to skip errors.
   Do not re-import database_setup; it contains DROP TABLE statements.
4. Copy functions/get_prices_and_macros.php over that one file in your site.
   Or apply recipe_nutrition_display.patch instead; they are the same change.
   This makes the recipe-selection page honor used_servings just like the
   existing recipe-details page and final shopping list already do.
5. Back up and replace BOTH scripts/modify_item.php and functions/modify_pantry.php
   with the supplied files. Then reopen Edit Items before making any changes.
   This fixes the existing editor rejecting blank prices while saving URLs.
   Unknown prices remain NULL. No extra SQL needs to be run for this editor fix.

RESULT
Seven recipe tables, seven recipe_lists entries and fourteen matching HTML files.
The repository dump is missing 13 of the 43 ingredient records used here.
Actual inserts are decided by ingredient name at import time, not hard-coded IDs.
No existing food record is overwritten. Existing recipes and weekly selections
are left alone. Repeating the import does not duplicate these recipe rows or foods.
DDL can commit before the data transaction; this is not an all-or-nothing schema
rollback. If interrupted, inspect the error and rerun after resolving it.

The import's data operations passed local tests using SQLite with the MySQL

Nothing has been run on your live server.

SERVINGS: ONE MEANS ONE NUTRITION SERVING
- Item calories/protein/fat/carbs/fiber are per ONE stated nutrition serving.
- New items have servings=1, following your one-serving entry convention.
  Existing item servings values are not modified. Every new recipe row supplies
  an explicit used_servings value, so the older fallback multiplier is bypassed.
- qty is the number of purchases, e.g. 2 salsa jars or 1 four-stick butter pack.
- used_servings is the number of those nutrition servings actually consumed in
  the entire seven-meal recipe. A partial package does not count as a whole one.
- Batch nutrients = sum(item nutrient per serving * used_servings).
- Nutrients per meal = batch nutrients / 7.
- Example: one tablespoon of the existing olive oil is 1 used serving = 120 kcal
  in the batch, about 17 kcal per meal. One 8-oz cream-cheese block is 8 one-oz
  servings, not 7 blocks or 7 separate recipe batches.
- Each imported recipe is ONE whole seven-meal batch: choose Portions = 1 when
  adding that recipe; keep Portions for Prep = 7 to see per-meal nutrition.
  Choosing 7 in the recipe selector multiplies it into seven batches (49 meals).
- The SQL does not change your global portions setting.

WHAT IS ESTIMATED / WHAT TO CHECK
The dump stores nutrient numbers but no serving-size text or gram weights.
The unit assumptions below therefore matter. They are conventional serving sizes,
not verified labels for all of your existing products. Existing numbers are
preserved even where they differ from the standalone recipe estimates.
New nutrient values are generic estimates per ONE stated serving, not scraped
Walmart label data. New prices are NULL. The new servings field defaults to 1,
not a guessed number of meals or a claimed number of servings in a retail package.
Your current UI can show a NULL price as zero: this means unknown, not free.
When you update an item's nutrition from a product label, make sure its serving
size matches the unit below; otherwise adjust used_servings to the recipe amount
divided by the new label-serving amount. In particular, check the existing pork
shoulder record's raw/cooked basis and serving size before trusting its totals.

PURCHASE QUANTITIES
Variable-weight meat Qty 1 means enough packs to provide 4 lb after the specified
trimming. Select sufficient actual weight; a smaller advertised pack is not enough.
Mushrooms assume three 8-oz packs. Broth assumes one 32-fl-oz carton per recipe;
buy two if splitting that recipe into two pressure-cooking batches. Garlic qty
follows the existing Garlic Clove name literally. Tap water is qty 0 and is not
added as a paid purchase. Sides and optional toppings are not in the recipe tables.
Shared pantry packages can appear multiple times if you add several recipes at
once, as in your current application; adjust the pantry/shopping quantity normally.

WALMART LINKS
Known existing URLs are preserved. The new links below were located in Walmart
indexed listings; availability and local pricing are not guaranteed. Unresolved
links stay blank, with no invented product IDs. The app itself appends #id=ID,
using the real ID assigned by MySQL. Do not put #id into the stored URL or the
app will add it twice. The SQL's final report shows the resulting complete links.
Source: php/final_shopping_list.php in your repository.
